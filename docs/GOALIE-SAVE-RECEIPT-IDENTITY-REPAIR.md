# Goalie save receipt identity repair

Base: cfc020e89348ea8c37cc64df73931c82ba3181dd. Installed game: 26141904.

The E5CE retest produced committed companion records while the goalie selection displayed a save failure. The checkpoint marker write/readback no longer logged an error. The save consumer compared `CampaignState._runDataRepository.Pointer` with a receipt from `RunDataRepositoryV2.SaveToPersistentStorage`. These are different native objects: the campaign owns an `IRunDataRepository` implemented by `RunDataRepository`, which contains its separate `_runDataRepositoryV2` storage object. The incorrect comparison prevented the caller token and admission receipt from being claimed. The caller could consequently report rejection and restore its prior in-memory roster after the proposed roster had already reached storage.

The installed wrapper types independently establish both field types. Native inspection confirms `RunDataRepository.SaveRunData` at RVA 0x3F4ADC0 reads its nested V2 reference at +0x10 and calls V2.SaveRunData at 0x3F50560. V2 starts its state machine synchronously at 0x3F50704; the initial MoveNext serializes at 0x3F51D7F and calls SaveToPersistentStorage at 0x3F51D96 before its first await continuation at 0x3F51EB7. The existing scoped caller remains valid at admission; extending its lifetime or accepting unrelated receipts is unnecessary.

`SaveRepository` now resolves only the reviewed concrete facade and nested V2. SaveChange pins that object before publishing a mutation, SaveCampaign checks it again, and the bridge/admission consumer retains exact storage, caller token, run, model and operation checks. Unsupported facades or missing storage reject before mutation. The same erroneous facade comparison in the contract-match launch receipt check now uses this resolver; all durable receipt and attempt checks remain intact. Wrapper preflight also validates the two generated field getter signatures. No hooks, native addresses, compatibility contract sets or native baseline metadata changed.

Each completed change emits one bounded diagnostic containing run, outcome, explanatory message, expected storage identity, operation, receipt storage identity, native result/error, reconciliation, checkpoint revision, no-local-write and failure reason. The menu callback uses the same receipt description. These logs do not replace persisted-pair proof or relax rollback requirements.
